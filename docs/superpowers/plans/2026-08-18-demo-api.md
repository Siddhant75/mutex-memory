# Demo API and Lambda Handler Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose the complete Mutex Memory MVP flow through one validated Lambda-compatible JSON API.

**Architecture:** A demo evidence reader keeps SQL below the transport layer. A dependency-injected router owns HTTP semantics, while a thin AWS payload-v2 adapter and lazy runtime composition make the same core deployable as one Lambda.

**Tech Stack:** TypeScript, Zod, Vitest, `pg`, AWS Lambda Function URL payload format 2.0, existing Mutex Memory workspaces.

**Spec:** `docs/superpowers/specs/2026-08-18-demo-api-design.md`

## Global Constraints

- Preserve the frozen Phase 1 transaction and retry implementations.
- Support only the four routes defined in `HACKATHON_MVP.md`.
- Keep CORS in Function URL infrastructure, not handler responses.
- Do not add API Gateway, authentication, web frameworks, deployment resources, frontend code, or real effects.
- Never expose database URLs, AWS errors, SQL text, or raw model output in `500` responses.
